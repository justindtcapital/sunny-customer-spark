# Server utils rules (knowledge harvest, Drive, Gmail)

- Mailbox tokens: per-mailbox Gmail refresh tokens are stored AES-GCM encrypted in the private "Mailbox Tokens" sheet tab, accepted only when Google confirms the consenting account equals GMAIL_KB_MAILBOX — app sign-in is an allowlist, so Google is the identity proof.
- Alias-harvested (gmail-*) activities count as registered activity only after Activity Review confirms them (review state shared with Notes Imports in Harvest State) — keeps automated tagging from polluting dashboards.
- KB Drive meeting files are imported by moving them into Meeting Notes/<PortCo> and marking appProperties.vp=1; files Venture Pulse created carry the same mark and are never re-imported — keeps Drive scans idempotent.
- Network (NWK) notes come from the NWK@ alias (GMAIL_NWK_ALIAS, default nwk@dt-capital.net) or "NWK" in a note title; on review, tagged contacts get one Interaction Trail row each (Source Ref kb:<recordId>, deduped) and the review stores their emails — keeps contact history traceable to the source note.
- New KB files land in Drive 'Unfiled Documents' and move to Meeting Notes/<PortCo>, PortCo Operations or Network Updates only on review — Drive mirrors reviewed state.
- Personal Granola keys are encrypted in Cloud, keyed by verified auth UUID; connection/import operations require a confirmed roster email — typed names cannot select another person's credentials. CRM data stays in Sheets.
- Google Groups rewrite From to the alias; parseMessage unwraps the real sender from X-Original-Sender/Reply-To so per-owner inboxes attribute correctly. Gmail harvest cursors overlap 2 days because existing threads are skipped.
- Contact imports read unified Contacts once for identity checks and append literal cells before exact read-back verification; duplicate view matches and Sheets coercion must not strand successful imports.
- Interrupted imports get a self-service "Check what was saved & unlock" (import-reconciliation planner): it reads fresh Contacts, records per-person evidence and releases only that operation's lock, never writing people or replaying — users recover without risking duplicates.
- Target/Prospecting appends write literal cells so read-back verification matches.
- Morning Brief: read-only enrichment of Claude Cowork's daily email, one Cloud morning_briefs row per owner/day (single-flight claim, email sent once via the linked google_mail connector); cron answers fast and finishes via waitUntil; unknown people go to reviewed paste (per-person or all, also via the emailed /brief?add= link) — never auto-writes CRM. It reads Cowork's full email (searchGmailRaw maxBody; the 3,000-char default cut off the trailing contacts table). People match by Cowork-supplied email before name; nickname-compatible names ("Matthew"/"Matt") are possible matches, never new — prevents duplicate contacts. Each meeting has one subject (title PortCo, else outside company profiled via Google-grounded Gemini); body-only PortCos are name-only mentions and scheduling sentences are stripped — keeps cards about who you're meeting.
- Person event links (Network and Prospecting) share the CRM "Events" tab keyed by Contact URID then email; Prospecting adds are deduped after fresh reads, removals stamp "Removed At" (never delete), and the legacy Targets "Event" cell reads as an Invited link and is never overwritten — so people keep many events and provenance.
- Contact merges keep one record (its URID) and archive the others in place (Relationship Status "Merged", "Merged Into"; email moved to the main record). The main record's "Merged URIDs" pulls archived history in at read time, and the append-only "Contact Merges" tab logs full before/after rows first — no child rows are rewritten, and undo restores only cells nobody edited since.
- Vic's Asana tools are retired; webSearch uses Google-grounded Gemini search first (Perplexity fallback). Extended read/proposal tools live in vic-read-tools.server.ts and vic-propose-tools.server.ts and never write without human approval in VicChat review cards.
- Event-tagged uploads (Network and Prospecting) write explicit Attended person links plus Attended tracker attendee rows; a stronger status upgrades an existing row in place (planAttendeeWrites, Attended > Registered > Invited) and never downgrades — the legacy Event cell alone reads as Invited, so attendee lists used to land as invitees.
- Vic event attendee reads (getEventDetails) reuse eventPeople and the pure vic-events shaper over the same tracker, Network, Prospecting and tag reads as the event panel — so V.I.C. lists exactly the people the app shows.
- Vic campaign reads (searchCampaigns, getCampaignDetails) read Campaigns, Campaign Members and latest Campaign Results through the pure vic-campaigns shaper with offset paging — so V.I.C. lists every member and normalized response the Campaigns page shows.
- Core list reads (contacts, prospects, portfolio companies) go through lastGoodReader: on a failed Sheets read they serve the last real result or fail visibly — there is no sample/placeholder dataset, so made-up companies can never appear.
- Signals page reads the Sheets "Signals" tab strictly (outage = unavailable, missing tab = empty) and NEWS@ sends carry a VP-Signal-Id marker that ingestion skips. The daily scan is a scheduled /api/public/cron/signals-scan call that hands the minutes-long scan to Inngest (event signals/scan.requested) — Worker background time is too short to finish it inline. The daily Inngest run has three steps (news@ inbox filing, main scan, enterprise watch over a rotating batch from src/lib/enterprise-watch.ts); network-company stories must name the company they're filed under, since the model sometimes files news under a suggested person's employer.
- Signal "V.I.C. suggests" (signal-match.server + pure src/lib/signal-match.ts) runs only when someone clicks "Who might care?" (one AI call returns a gist per pick for the shortlist plus the detail shown on click) and is read-only: the model may only pick from Council/Hot/Warm people (plus anyone at the company in the news) and real PortCos; person lines carry recorded prior PortCo intros and latest note summaries (priorHistory), and the shown "On record" line comes from the record, not the model; picks are validated against those records; actions reuse the email draft dialog, createVicFollowUpFn and a seeded V.I.C. chat — so suggestions can't invent people or write data on their own.
- Signal card headlines come from one pure picker (src/lib/signal-headline.ts): the Signals "Headline" column (last column, written by the scan prompt or the daily signal-headlines step, which only fills empty cells), else a real article title, else the shortened lead fact — never a "Company — Category" label; recommendation Subjects are email subjects, not titles. Feed, Morning Brief and V.I.C. all use it so headlines match everywhere.
- Signals scan news comes from Google up front on every scan (google-news.server: Google-grounded Gemini search kept only when Google tied a story to a source, resolved to the real article URL, long lists rotate daily; plus Google News RSS headlines) and Perplexity only when PERPLEXITY_API_KEY exists; Event Registry is not called — its free quota ran out and silently emptied scans.
- Sheets reads go through a database copy (sheet-mirror.server, pure planner src/lib/sheet-mirror-plan.ts): every save hits Sheets first, then sheetsFetch applies the same change to the copy (or marks the tab stale); non-fresh reads serve the copy, fresh reads and stale/old/missing copies go to Google and refresh it. The /api/public/cron/sheets-mirror schedule checks Drive modifiedTime and batchGets changed tabs; private/backup tabs are never copied. Sheets stays the source of truth and any database failure falls back to direct Google reads — this keeps page loads out of the 60-reads/minute quota.
- Notes inbox people matching (uniqueReviewPerson, suggestPeople) uses per-directory lookup indexes, and identical inbox loads share one client request — linear scans over every contact made My Actions take 15–30s.
- addContactRow is the one duplicate gate for every add path: it reads Contacts fresh and, via findExistingContact (src/lib/contact-identity.ts: same email, LinkedIn, or full name + company across Network and Prospecting, Merged rows excluded), returns the saved record instead of appending; Prospecting "Promote to CRM" flips the same row to Cold in place — separate per-path checks with different scopes kept creating copies.
- Review-card people matching: the directory excludes Merged rows and carries URIDs; 2+ exact records for one person are surfaced as merge-or-pick (never auto-linked), and the inline PeopleFinder (src/components/knowledge) ranks via src/lib/people-finder.ts and edits saved people by URID through mergeContactFields — so duplicates get fixed where they're found.
- Bulk email-duplicate cleanup plans with src/lib/contact-cleanup.ts (shared-email groups; keep the record holding the most recent status — latest of Date Added or a Rating History status change — newest record among ties) and writes the same Contact Merges log rows as manual merges, so each merge is undoable from Recent merges.
- appendTargetRows (every Prospecting add: campaigns, prospect/account search, theses, V.I.C., imports) runs the same findExistingContact gate over fresh Contacts plus its own batch and returns added/existing counts — per-path Targets-only checks let Network people come back as Prospecting duplicates.
- Twilio WhatsApp (`/api/public/twilio-whatsapp`, `twilio-whatsapp.server.ts`, `vic_whatsapp_links`): HMAC-verifies `X-Twilio-Signature`, checks linked E.164 phone, runs V.I.C. via `runInBackground` into a `"WhatsApp"` `vic_threads` chat, and replies via Twilio REST API.
